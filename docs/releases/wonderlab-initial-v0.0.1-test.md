# 初始 0.0.1 测试基线：上传与人工切版

这套候选资源用于验证初始版本和历史选版，不切换旧正式入口。当前作者源码、两个手写示例及软件内置包统一为 `0.0.1`；旧发行历史、Release 和课程版本锁继续保留。

## 准备资源与软件

候选交付目录是仓库内被忽略的 `dist/wonderlab-initial-0.0.1-20261028/`。不要把它整体压缩后作为拓展包导入；软件需要其中每个独立产品 ZIP。

使用包含本次修改的开发软件。旧安装包不会因作者源码重置而自动更新内置版本；安装包验收应使用隔离的 WonderLab-test，不覆盖正式软件。使用空白测试工程，不覆盖原课程，不删除旧安装数据。

Git tag 应指向审阅并提交后的公开库源码；软件侧使用包含对应适配的代码。仅本地提交不会更新 GitHub 分支，创建远端 tag 前先核对目标提交已同步，不要将旧提交描述成本次产物的完整源码。以下步骤不包含自动推送。

## 上传两个候选 Release

目标仓库为 `hiwonderk12/scratch-product-extensions`。在 GitHub 的 Releases 创建候选发行，勾选预发布，不设为正式最新版。tag 和资产文件名必须与下表完全一致：

| Tag | 上传目录（相对交付目录） | 内容 |
| --- | --- | --- |
| `wonderlab-initial-v0.0.1-20261028` | `assets/wonderlab-initial-v0.0.1-20261028/` | 全部 41 个 `*-0.0.1.zip` |

不要覆盖旧 tag 或旧资产。`release-manifest.json` 可用于核对文件名与本地指纹；其中 SHA256 只是交付指纹，不是下载协议新增的必填字段。

额外光敏版本仅用于观察切换效果，作者目录仍是 `0.0.1`，不将演示规则当作真实传感器更新发行。

将交付目录 `github-files/` 下的文件按原相对路径上传至仓库 **wonderlab 分支**：

```text

├─ catalog.json
├─ catalog-baseline.json
└─ products/<分类>/<产品>/catalog.json
```

必须上传全部 41 份产品历史子目录；只上传根 JSON 或只创建 Release 都不足以让软件发现并下载包。旧根 `catalog.json` 和旧 `products/` 历史不动。

## 人工验证

1. 在软件的原生测试目录连接上述分层切版入口，启用“允许候选包”，读取目录。旧客户端不认识根 v3 时不能用平铺成功代替分层验收，应改用包含分层支持的软件。
2. 回到主控拓展页，显式选用 Aimech `0.0.1`。若当前工程使用旧快照，按配套确认切换；同版内置资源无需重复安装。
3. 在模块拓展页选择光敏 `0.0.1`，将读取积木用于程序，确认 Python 包含 `light.read_value()`，保存 V1 工程。
4. 从同一卡片的版本下拉下载 `0.0.2-test.20261028`。仅下载时当前工程应仍使用 V1，Python 不变。
5. 显式选择使用 V2，确认切换。产品／分类名称应出现“切版演示”；积木文本本身没有附加标记。读取表达式应变为 `(light.read_value() + 1)`。
6. 切换简中、英文、繁中和韩文，分别检查名称标记、菜单和积木；参数值、工程版本锁和同一版本的 Python 不应因界面语言改变。
7. 保存另一份 V2 工程，退出后断网重开，分别打开 V1、V2 工程。应恢复各自版本、参数、素材及手写代码，不因离线自动换版。
8. 检查缺少锁定版本时的明确提示；不要删除自己课程依赖的包来做负向验证。

成功标志是两个版本可显式选择、下载不自动升级、两份工程离线恢复各自版本。ZIP 检查通过不能替代真实界面、安装包或硬件验收。

## 常见现象

- 默认正式“检查版本”仍出现旧调试版本：本轮刻意保留旧正式入口；先确认已手动连接测试源。
- 目录能读但下载失败：检查两个候选 Release 是否已发布为可访问的预发布、tag 与资产名是否匹配；草稿资产不能作为公开下载源。
- 根能读取但缺产品：检查全部子目录已按原路径上传，而非上传成一份目录 ZIP。
- 旧项目仍使用旧版：这是精确版本恢复的预期；测试新基线应新建工程或显式确认配套切换。

旧历史保留不代表已验证所有线上资产可访问。人工联调通过后，再独立决定正式入口的迁移、软件兼容版本及发布顺序。
